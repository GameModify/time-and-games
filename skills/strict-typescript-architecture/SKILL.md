# Строгий TypeScript и архитектура

Применяй эти пользовательские стандарты к TypeScript-коду, тестам, скриптам и конфигурации. Сначала прочитай AGENTS.md, package.json, tsconfig, ESLint и описание архитектуры проекта. Учитывай явно заданную область задачи: небольшая правка не означает разрешение переписать весь посторонний код.

## Типизация и данные

- Пиши новый код на TypeScript. В Vue используй `<script setup lang="ts">`.
- Включай `strict`, `noUncheckedIndexedAccess`, `noUnusedLocals`, `noUnusedParameters`, `noImplicitReturns`, `noFallthroughCasesInSwitch`. Сохраняй более строгие настройки проекта.
- Используй ESLint `strictTypeChecked`, проверку промисов и type-only imports; предупреждения должны завершать проверку ошибкой. Запрещай локальные отключения через `linterOptions.noInlineConfig: true`; не переопределяй отдельные strict-флаги TypeScript в `false`.
- Не обходи проверки через `any`, `@ts-ignore`, `@ts-nocheck`, отключение правил, двойные приведения `as unknown as` или необоснованный `!`.
- Между модулями передавай типизированные модели, интерфейсы и DTO. Не используй JSON-строки, `unknown` или универсальные словари вместо предметного контракта.
- Разбор и сериализация JSON допустимы на границах HTTP, SQLite и резервных копий. Проверяй внешние данные Zod-схемой или эквивалентным валидатором до передачи в предметную логику. `unknown` допустим внутри адаптера и для сужения ошибок/внешних значений.
- Выводи типы контрактов из схем, чтобы проверка времени выполнения и TypeScript не расходились. Формы могут иметь отдельную модель, например пустую строку вместо числового нуля. Собирай DTO записи явно, без метаданных формы.

## Размер и сложность

- Каждая функция, метод и callback: максимум 20 строк. Считай сигнатуру, пустые строки и комментарии; IIFE тоже проверяются.
- Когнитивная сложность каждой функции не выше 20. Это отдельный показатель ветвлений и вложенности, а не число строк.
- Закрепляй оба ограничения как ошибки ESLint: `max-lines-per-function: ['error', { max: 20, IIFEs: true }]` и `sonarjs/cognitive-complexity: ['error', 20]`.
- Не делай исключений для тестов, скриптов и обработчиков. Более строгие лимиты допустимы.
- Выделяй самостоятельные операции с понятными входами и результатами. Не уплотняй выражения, не прячь алгоритм в класс или набор обёрток только ради прохождения линтера. Длинные тесты разделяй на сценарии и именованные данные, сохраняя проверки поведения.

## Архитектура

Сохраняй явных владельцев состояния, направленные зависимости и публичные интерфейсы модулей. Проверяй границы импортов автоматически; при добавлении alias или динамического импорта расширяй проверку под новый способ разрешения модулей.

Для Vue прочитай [references/vue-architecture.md](references/vue-architecture.md). Не навязывай FSD проектам с другим стеком или явно выбранной архитектурой.

## Проверка результата

1. Проверь конфигурацию и используй автоматические проверки репозитория. Для UI дополнительно проверь изменённый сценарий в доступном браузере; для хранения — сохранение, перезапуск и восстановление, если они затронуты.
2. Перед завершением один раз запусти полный набор: проверка типов, архитектуры, ESLint без предупреждений, форматирования, сборка и подходящие тесты. По ходу работы используй точечные проверки. Не повторяй полный набор без новой причины.
3. Скрипт `scripts/verify-project.ts` проверяет эффективные настройки TypeScript/ESLint для исходников, тестов, скриптов и TS-конфигурации. `--audit` проверяет только настройки; обычный запуск затем последовательно выполняет scripts `check`, `build`, `test` через Node 24.12+. Зависимости TypeScript, ESLint и Zod берутся из проверяемого проекта. Пакет должен содержать tsconfig.json и указанные npm scripts; для monorepo выбери конкретный пакет.

```powershell
node <путь-к-скиллу>/scripts/verify-project.ts --audit <корень-проекта>
node <путь-к-скиллу>/scripts/verify-project.ts <корень-проекта>
```

Автоматическая проверка настроек не заменяет чтение кода: оцени смысл декомпозиции, контракты между модулями и отсутствие скрытого общего состояния. При отсутствии проверки архитектуры добавь подходящую для выбранного проекта и включи в `check`; до этого не объявляй архитектуру проверенной. Если проверка недоступна, сообщи конкретное ограничение.

В Time & Games версия скилла хранится в `skills/strict-typescript-architecture`, `npm run quality:audit` проверяет настройки, `npm run verify` выполняет полный набор. Правила импортов описаны в docs/architecture.md, автоматизированы scripts/check-architecture.ts и входят в `check`.

Скилл задаёт правила разработки и проверки. Сам по себе он не запускается фоном: обязательность обеспечивают команды репозитория и CI. Он не даёт отдельного разрешения на публикацию, merge или деплой.
