# Правила разработки Time & Games

Выполняем работу **в папке** `%USERPROFILE%\Desktop\Мой сайт`; основная ветка — `main`.

## Ветки и коммиты

- Каждая законченная задача разрабатывается в отдельной ветке от `main`: `feat/*`, `fix/*`, `refactor/*`, `docs/*`, `chore/*`.
- Коммиты называются по Conventional Commits: `feat(timeline): add overlapping sessions`, `fix(timer): stop session`, `docs: update setup guide`.
- Один коммит может охватывать несколько промежуточных микроизменений; не нужно коммитить каждую правку строки.
- Не делаем прямые feature-коммиты в `main`. Создаём PR, описываем поведение и проверки; после merge удаляем ветку.
- Для обычных PR используем **Squash and merge**, чтобы история `main` была читабельной. Ветка `main` должна проходить CI.
- Описание PR краткое: итоговое изменение и выполненные проверки. Пиши для разработчика, который не видел переписку. Не включай историю запросов, упоминания пользователя или Codex, промежуточные решения и журнал исправлений. Существенные технические ограничения указывай кратко, только если они влияют на проверку или использование изменения.

## TypeScript и линтер

Клиент, сервер, тесты и скрипты пишутся на TypeScript. Компоненты Vue используют `<script setup lang="ts">`. Node.js должен быть версии 24.12 или новее. Типы внешних данных выводятся из Zod-схем и проверяются при чтении. Не используй `any`, подавление ошибок TypeScript или отключение проверок для обхода типизации.

`npm run check` включает `vue-tsc`, границы архитектуры, ESLint `strictTypeChecked` с правилами Vue и Prettier. Проверка завершается ошибкой при любом предупреждении. `npm run typecheck` подходит для быстрой проверки типов, `npm run format` форматирует код. Все проверки обязательны в CI.

Каждая функция, метод и callback ограничены 20 строками и когнитивной сложностью 20. `max-lines-per-function` считает также сигнатуру, комментарии и пустые строки; `sonarjs/cognitive-complexity` проверяет ветвления и вложенность. Правила действуют в клиенте, сервере, тестах и скриптах. Выделяй самостоятельные операции и именованные тестовые данные; не обходи лимит сжатием строк или исключениями.

Между модулями передаются типизированные модели и DTO. JSON допускается только на границах HTTP, SQLite и резервных копий. Разбор внешних значений выполняется через Zod в адаптере до передачи в предметную логику. ESLint запрещает `JSON.parse/stringify` вне этих адаптеров.

## Когда запускать тесты

**Не запускать полный набор после каждого микроизменения.** По ходу задачи допустимы быстрые локальные/точечные проверки. Когда фича или исправление полностью готово, **до завершающего коммита и PR** выполняем:

```powershell
npm run check
npm run build
npm test
```

Для изменений интерфейса — ручная проверка в браузере, для изменения API — подходящие проверочные запросы. GitHub Actions запускается на **PR в main** и на **изменениях main**, а не на каждом push в незавершённую feature-ветку.

## Конфиденциальность и данные

Не коммитить `data/` (SQLite, WAL, JSON-экспорты), `.env`, токены Steam/API, `node_modules/`, `dist/`, логи или личные данные. Проверить `git status` и `git diff --cached` перед push. Никаких секретов в сообщениях коммитов и PR.

## Branch protection

Желательная настройка для `main` в GitHub Settings → Rules → Rulesets: **Require pull request**, **Require status checks (verify / Build, lint and tests)**, **Block force pushes**, **Block deletions**. На некоторых тарифах GitHub правила private repo могут быть ограничены. Текстовые правила и CI работают независимо, но сами по себе не блокируют прямой push.
